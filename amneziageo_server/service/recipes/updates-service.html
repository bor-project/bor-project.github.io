An update server apart

The releases of the client can be kept on an update server apart rather than in the panel: on another host, on another disk, or one for several panels. It is the same update server as “Own” in the panel, only as a program of its own: it hands the releases to the apps without authorization and takes them by a token from its own window, from the panel or from a script. A panel on its host hands the releases out itself, see Client updates, so a host carries one of the two: the panel or the update server. In the example, the server stands at updates.example.com, and the panel takes its releases by the address.

Install the server

It takes Debian 12 or newer or Ubuntu on amd64 or arm64, root and room for the releases: one release of the client takes about 800 MB. The server needs neither the amneziawg module nor forwarding. As root:

curl -fsSL https://github.com/bor-project/amneziageo_server/releases/latest/download/amneziageo-server \
  -o /usr/local/bin/amneziageo-server
chmod 755 /usr/local/bin/amneziageo-server
amneziageo-server install

Answer the first question, What to install, with 2 (Client updates server). The script looks the host over (the system, memory and disk, Docker, ufw, the ports taken, the Let’s Encrypt certificates), asks its questions, prints the plan and, once you agree, does everything on the list.

Docker takes Docker with its compose plugin and a running daemon: where something lacks, the script prints the commands that put it on and exits without changing anything. The answers can be put in a file beforehand and given with amneziageo-server install --answers <file>, as for the panel.

What the installation does:

  • upgrades the system when agreed; when a new kernel comes, it reboots the host, and the same command goes on after the reboot with the same answers;
  • gets a Let’s Encrypt certificate for the name of the server (certbot, the check on TCP 80, renewals by certbot.timer) or takes the one the host already holds; without a name the server answers under a certificate of its own, and the apps check it by the digest the panel names;
  • makes the token and a random path of the window;
  • as a service: downloads the archive of the server from the latest release of the channel, checks it against the list of the release signed with the key of the releases and puts on the amneziageo-updates service; in Docker: puts the compose project in /opt/amneziageo-updates and starts the amneziageo-updates container from the image ghcr.io/bor-project/amneziageo-updates of the same release, on the network of the host;
  • opens the port in ufw or turns ufw on;
  • prints the address of the releases for the panels and the apps, https://<name or address of the host>:<port>/, the address of the window and, once, the token.

Where things lie:

From then on its menu looks after the server: amneziageo-server on such a host opens the menu of the update server with the update and the rollback, a new token, a new path of the window, the port, the certificates and the firewall.

Without the menu

The image runs without the menu as well, its settings are the Updates__* variables:

Variable What it sets
Updates__Listen__0 address and port, like *:8445; not set - port 8445 on every address
Updates__Path the path before the releases; empty - the root
Updates__WebPath the path of the window; not set - the file web-path in Updates__Etc: on the first start, the server writes a random path there
Updates__Directory the directory of the releases, /var/lib/amneziageo-updates
Updates__Etc the directory of the token, the path of the window and the own certificate, /etc/amneziageo-updates
Updates__Token, Updates__TokenFile the token or the file holding it; not set - the file token in Updates__Etc: on the first start, the server writes a new token there
Updates__Certificate, Updates__CertificateKey the chain and the key in PEM; not set - a certificate of its own

GET /health answers 204; the health check of the container stands on it.

The window of the server

The address of the window is https://updates.example.com:8445/<path>/: the installation and item 9 View Current Settings of the menu print the path of 16 letters and digits, item 7 Reset UI Path gives a new one. The window is signed into with the token of the server.

Once signed in, the window shows the address of the releases for the panels and the apps with “Copy”, the directory of the releases with the room left, and the “Releases” table. Releases are created, changed and removed as on the tab of the panel, see Releases. A window opened before a new token from the menu goes back to the sign-in at its next request to the server: sign in with the new token.

Connect it to the panel

  1. “Settings” - “Client updates”: turn on “Hand out updates to clients”, “Source” - “Address”.
  2. “Address” - https://updates.example.com:8445/, “Token” - the token of the server, “Check”. The answer is “answers: releases 0, 0 B”.
  3. “Save”. The panel keeps the certificate of the server and names it to the apps.

The firewall of the host of the server must let its port in: the apps download the releases straight from the server, not through the panel.

Put a release

“Create update” in the window of the server or on the tab of the panel with “Address”: version, channel, files, “Confirm”, see New update. An app with a configuration of this panel sees the server in “Connections” - “Update server” by its address; with “On by default” set, the app takes it while no update server is picked by hand, and offers the release of its channel when it is newer than the installed version.

Check

  • curl -s -o /dev/null -w '%{http_code}\n' https://updates.example.com:8445/health - 204.
  • curl https://updates.example.com:8445/beta/update.json - the manifest of the newest stable release or beta; 404 while there is none.
  • amneziageo-server status on the host of the server: whether the server and its window answer, the certificate, the port in ufw.
  • The “Client updates” row in the “Services” of the Overview of the panel stands without a reason.

A container beside the panel from item 30

The update server used to go on with item 30 of the menu of the panel, in a container beside it. Such a container is looked after by the same item 30: it shows in the menu of the panel while the container stands, and it moves the container to the latest image, makes a new token, shows the log and takes it off. The first update moves the container to the network of the host on the same port, and the port and the certificate into /etc/amneziageo-updates/updates.env; the releases and the token stay as they were.
