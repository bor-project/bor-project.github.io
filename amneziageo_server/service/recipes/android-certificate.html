A certificate older Android trusts

The task: Android before version 14 does not open the panel or the subscription of the server, while a computer and a newer phone open them. Almost always the chain of the certificate is to blame: it ends at the ISRG Root X2 root, which these phones lack. They hold ISRG Root X1, and the chain has to reach it.

1. Signs

  • The browser on Android before 14 says the connection is not private and does not open the panel or the subscription page.
  • Apps that download the subscription by themselves answer with a connection error.
  • The “Services” card on the Overview says “the chain ends at ISRG Root X2: Android before 14 will not read the subscription” in the “Subscriptions” line and in the line of the certificate.

Under such a chain the subscriptions are off for every client, and the AmneziaGeo app shows the subscription with the “!” sign, see A certificate not every client takes.

2. Check the chain

The command checks the chain from any machine with OpenSSL, the server itself included. Put the name of the server for <name> and the port of the panel or the port in the address of the subscription for <port>:

openssl s_client -connect <name>:<port> -servername <name> < /dev/null 2> /dev/null | grep -E '^ +[0-9]+ s:|^ +i:'

The s: lines name the certificates of the chain, the i: lines name who issued them. Look at the last i: line:

  • ISRG Root X1 - good: every Android since 7.1 holds this root;
  • ISRG Root X2 or Root YE - bad: Android before 14 does not take such a chain.

A good answer, an RSA key:

 0 s:CN=vpn.example.org
   i:C=US, O=Let's Encrypt, CN=YR1
 1 s:C=US, O=Let's Encrypt, CN=YR1
   i:C=US, O=ISRG, CN=Root YR
 2 s:C=US, O=ISRG, CN=Root YR
   i:C=US, O=Internet Security Research Group, CN=ISRG Root X1

A bad answer, an ECDSA key with the short chain:

 0 s:CN=vpn.example.org
   i:C=US, O=Let's Encrypt, CN=YE1
 1 s:C=US, O=Let's Encrypt, CN=YE1
   i:C=US, O=ISRG, CN=Root YE
 2 s:C=US, O=ISRG, CN=Root YE
   i:C=US, O=Internet Security Research Group, CN=ISRG Root X2

The default chain of Let’s Encrypt reaches ISRG Root X1 for an RSA key and for an ECDSA key alike. For ECDSA it holds one link more: after ISRG Root X2 comes ISRG Root X2 again, signed by ISRG Root X1. A bad chain comes from the short chain chosen at issuing (--preferred-chain of certbot) or from a program that picks the chain by itself. The chain of an RSA key does without ISRG Root X2, so the menu issues RSA.

When not the panel but nginx, 3x-ui or another proxy answers on the port, the command shows its certificate, and that is the one to fix.

The Key Type line of certbot certificates names the type of the key of a certificate on the host. The “Certificates” entry of item 22 of the console menu prints it too.

3. An RSA certificate from certbot

Item 22 of the menu, SSL Certificate Management, its entry “get a Let’s Encrypt certificate”, gets a certificate with an RSA 2048 key. When a certificate of the same name is there already with an ECDSA key, the menu issues it again. By hand on the host:

certbot certonly --standalone --preferred-challenges http --key-type rsa --rsa-key-size 2048 --cert-name <name> -d <name>

The same command with --force-renewal moves an ECDSA certificate issued already to RSA. certbot writes the type of the key into /etc/letsencrypt/renewal/<name>.conf (key_type = rsa), and renewal keeps it. A certbot before version 1.10 does not know --key-type and issues RSA by itself.

No restart is needed: the panel reads the certificate again when the file changes on disk. A certificate from outside /etc/letsencrypt/live is put on the Certificates tab.

4. A certificate from another program

  • acme.sh (3x-ui gets its certificate through it too) issues an ECDSA ec-256 key by default and an RSA key with --keylength 2048. An ECDSA certificate lies in the <name>_ecc directory, an RSA one in the <name> directory. After issuing again, hand the new files to the server (--install-cert).
  • Caddy issues an ECDSA P-256 key by default and an RSA key with key_type rsa2048 in the global options or in the tls block.
  • Another program: issue an RSA 2048 key, or make sure by the check of section 2 that the last i: line is ISRG Root X1.

5. Check

On every port where the server answers over TLS the command of section 2 names ISRG Root X1 in the last i: line. The “Services” card on the Overview no longer names a reason in the “Subscriptions” line and in the line of the certificate.
