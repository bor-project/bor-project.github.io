Client updates Only in the AmneziaGeo appThe AmneziaGeo app takes its updates from the server: the server names where its releases lie, and the app checks them there under the certificate of the server.Other AmneziaWG clients do not get this: they get only the configuration file.Learn more

The tab hands out your releases of the client to the AmneziaGeo apps in place of the releases of the project on GitHub: a build with your own changes, say, or a version you checked yourself. The releases lie on an update server: in the panel itself (“Own”) or in a service apart (“Address”, see An update server apart). The tab is seen by a role with the “Client updates” permission.

Serving

“Hand out updates to clients” turns the serving on and opens its settings, “Source” picks “Own” or “Address”. “Save” takes effect at once: the panel brings the releases up again, and when the host does not give the port, it keeps the former settings and names the reason under the buttons.

Own

Field What it sets
Directory where the releases lie; empty - the folder client-updates beside the database of the panel. Under the field, the free space and “reads and writes” when the panel can write there
Port empty - the port of the panel: the releases sit beside it, under its certificate; another port - a listener of their own under the certificate of the panel. A port the firewall keeps closed is marked in the “Services” of the Overview
Path what follows the port; random by default, “New path” makes another. On the port of the panel, the path cannot start with api, assets, the path of the panel or the path of the subscriptions
Token the key of the API of the releases for scripts; its start and end are seen, “Copy” puts it on the clipboard, “New token” makes another
Address for clients https://<host>:<port>/<path>/: the apps read the releases here
On by default an app where no update server was picked by hand takes this one

Address

“Address” is the https:// address of the service of the releases apart, “Token” is its token: the menu prints it once when it installs the service. “Check” asks the service now and writes “answers: releases N, size” or “does not answer: reason”; the panel itself asks it once every 5 minutes. The panel keeps the certificate the service answered under and names it to the apps, so a certificate of the service’s own does as well. The releases of the service are created and changed in the panel as the own ones are. “On by default” is as for “Own”.

Releases

The “Releases” table goes page by page: version, channel, date, files out of 20 and size. The menu of a row has “Change” and “Delete”; deleting asks to confirm and takes the release away with its files. The releases do not run out: they lie until they are deleted.

The channel sets who gets a release. An app on the “Stable” channel takes stable releases, on “Beta” - stable releases and betas, on “Test” - all of them; the channel is picked in “General” of the app, where “Test” shows only on a test build. Of the releases of its channel, the app takes the highest version, and a stable release wins over a beta of the same version. The app never installs a version below the installed one.

New update

“Create update” opens the “New update” window.

  • “Version” is four numbers, like 1.10.16.0; “Channel” is stable, beta or test; “Description” is one line of up to 256 characters.
  • “Release files” are the 20 names of a release with this version: the Windows installers for x64 and arm64, with .NET inside and without it (-fdd), the amneziageo and amneziageo-gui packages for amd64 and arm64, the Android APKs (the common one and one per architecture), the patches to the installers and the packages. Each name has “Choose file” and “Clear”, a patch also has “from version”: the version it updates from.
  • “Confirm” is open when at least one file is chosen and none carries an error. The files go to the server one by one, the row of a file writes “sending N%”.

A file is checked twice. The browser checks the name of the file against the name of the row and the “from version” at once. The server reads the file itself on upload: an installer is a Windows program of the right architecture, a package is a Debian package with the right name and architecture, an APK is an archive with the libraries of the right architectures, a patch is a patch to the installer or the package of the same name. A refusal goes into the row of the file, like “built for x64, not arm64”; the file stays chosen, and the others are uploaded. The size and the SHA-256 are counted by the server, and it builds the update.json of the release: version, channel, description, files with their patches.

“Change” opens the same window for a release: change the channel and the description, upload or replace a file, take a file away (until confirmed it is “to be removed”), fix the “from version”.

Archive

“Upload archive” opens the same window with the line “Zip archive instead of files”: a zip with the files of the release at its root or in one folder. update.json in the archive is optional: when it is there, the server checks the names, sizes and SHA-256 of the files against it, when it is not, the server builds its own. The version and the channel come from the window, and the names of the files must match them.

How the app finds the releases

While the serving is on, the answer of the server to the app (hello) carries the address of the releases, the “default” mark and the SHA-256 of a certificate: for “Own”, of the certificate the releases answer under, for “Address”, of the one the service answered under. The address of “Own” is built from the name the app came by. The app reads <address>/<channel>/update.json and the files beside it under a certificate the system trusts or the one named. In the app, such a server shows in “Connections” - “Update server”, see the site of the client.

A server of an earlier version says nothing about releases in its answer, and its apps take their updates from GitHub.
